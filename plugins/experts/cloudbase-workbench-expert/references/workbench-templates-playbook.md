# 云端工作台场景模板 Playbook

小微经营者已验证的场景模板目录。需求澄清时从这里挑最接近的起步：字段可以增删，但数据模型骨架别推翻重来。每个模板含四项：场景名（用户口语）、数据模型（表/字段建议）、角色/登录、交付形态。

## 单人经营模板（老板自己记）

| 场景 | 数据模型（表 + 字段建议） | 角色/登录 | 交付形态 |
| --- | --- | --- | --- |
| 库存管理 | `products`(名称, 规格, 单位, 安全库存, 当前库存) + `stock_moves`(date, product_id, 方向: 入库/出库, 数量, 备注) | 单人免登录；多店员 → 多角色版 | 库存列表 + 低库存预警 + 出入库流水 |
| 进货管理 | `purchases`(date, 供应商, 合计金额, 状态) + `purchase_items`(purchase_id, product_id, 数量, 单价) | 单人 | 进货单录入 + 历史单据 + 供应商台账 |
| 库存盘点 | `stocktakes`(date, 状态) + `stocktake_items`(stocktake_id, product_id, 账面数, 实盘数) | 单人 | 盘点表 + 差异清单（盘盈/盘亏） |
| 销售订单 | `orders`(date, 客户, 金额, 状态, 支付方式) + `order_items`(order_id, product_id, 数量, 单价) | 单人；店员开单 → 多角色版 | 订单列表 + 今日单数与金额 |
| 营业日报 | `daily_sales`(date, 营业额, 单数, 客单价, 备注) | 单人 | 日报录入 + 趋势图 + 月汇总 |
| 店铺收支 | `transactions`(date, 金额, 分类, 方向: 收/支, 备注, 凭证 photo 可选) | 单人免登录 / 开登录换设备同步 | 收支流水 + 分类汇总 + 利润粗算 |
| 客户/会员 | `customers`(姓名, 电话, 标签, 备注, 累计消费) + `customer_orders`(customer_id, order_id) | 单人 | 客户列表 + 消费记录 + 标签筛选 |
| 预约排期 | `bookings`(date, 时段, 客户, 服务项目, 状态: 待到店/已完成/爽约) | 单人；客户自助约 → 多人版 | 日历排期 + 到店确认 + 爽约统计 |
| 商品/菜品目录 | `items`(名称, 分类, 价格, 成本, 图片, 上架状态) | 单人 | 分类目录 + 价格管理 + 毛利一览 |
| 供应商台账 | `suppliers`(名称, 联系人, 电话, 结算方式, 备注) + `supplier_bills`(supplier_id, date, 金额, 已付) | 单人 | 供应商列表 + 应付账款汇总 |
| 成本与毛利 | `item_costs`(item_id, 成本, 售价) + 派生计算 | 单人 | 单商品毛利表 + 滞销排行 |

## 多角色模板（老板 + 店员）

| 场景 | 数据模型 | 角色/登录 | 交付形态 |
| --- | --- | --- | --- |
| 员工考勤 | `shifts`(员工, date, 上班时间, 下班时间, 时长, 异常标记) | 老板 + 店员，手机验证码登录 | 店员打卡页 + 考勤汇总 + 迟到早退提醒 |
| 排班表 | `schedules`(员工, date, 班次) + `shift_types`(名称, 起止时间) | 老板排班、店员只看自己 | 周排班表 + 店员端「我这几天的班」 |
| 店员开单 | `orders` 加 `created_by`（开单人） | 老板看全部、店员看自己开的 | 销售排行 + 交班对账 |
| 多店管理 | 业务表加 `store_id`；`staff`(员工, 所属门店, 角色) | 老板看全部门店、店长看本店 | 门店切换 + 各店日报对比 |

## 「从单人到多角色」升级路径

单人模板默认免登录（最快交付）。当用户说「店员也要记 / 店员也要开单」时，同一套代码加两样东西就升级：

1. **手机验证码登录**：按 agents md 固件环节 B 配置（app-auth patchLoginStrategy + 前端短信登录）
2. **按角色隔离数据**：业务表加 `created_by` / `role` / `store_id` 字段，RLS 默认「老板看全部、店员只看自己或本店」；共享类表（商品目录、排班表）放开全员可读

注意：不要为「可能多人」预先设计登录——先按单人交付，店员参与的需求真正出现时再升级，避免过度设计。
