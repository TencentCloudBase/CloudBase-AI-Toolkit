# 云上全栈交付 Playbook

把「要跑的东西」落到云上的映射表与交付标准。选型时从这张表起步，具体命令以运行时官方 skill 为准（本包不复制平台 API 细节，避免漂移）。

## 一、跑什么 → 部署到哪

| 要跑的东西 | 部署形态 | 什么时候选它 |
|---|---|---|
| Node.js / Python / Go 的 HTTP API | **HTTP 云函数**（代码包，标准运行时） | 单入口、按量、冷启动可接受 |
| Java / Rust / C++ / PHP / .NET / Ruby 等非标准运行时的 HTTP API | **HTTP 云函数（容器镜像）**；需要长连接或常驻时才用 **云托管（容器）** | 见下方选型原则：**看形态，不看语言** |
| WebSocket / 长连接 / 常驻服务 | **云托管** | 容器里自己起服务、自己管端口 |
| WebSocket / 长连接 / 常驻服务 | **云托管** | 容器里自己起服务、自己管端口 |
| 定时任务（每天跑一次的数据同步等） | **云函数定时触发器** 或 容器内 scheduler | 任务短选函数，任务长选容器 |
| 数据处理 / 批处理脚本 | **云函数** | 事件驱动、按次执行 |
| 纯前端页面 / SPA | **静态托管** | 只要一个能打开的网址 |
| 前端 + 后端一体 | 静态托管 + 云函数/云托管 | 前后端分开部署，各用合适的形态 |

**选型只看形态，不看语言**：任何语言都能打成镜像、以「自定义镜像」的方式跑在 **HTTP 云函数**上（依据：`cloud-functions` 的 `references/http-functions-custom-image.md`，工具侧由 `manageFunctions` 的镜像部署承担）。只有下面这几种才**必须**上云托管：长连接（WebSocket / SSE / 服务端推送）、常驻独立进程、需要访问 VPC 内数据库 / Redis、迁移现成应用。**带着 `Dockerfile` 但本质是无状态 HTTP 服务 → 优先 HTTP 云函数**，别默认上容器。

## 二、Docker 上云托管的流程（任意语言的通用路径）

1. **确认 Dockerfile** —— 没有就生成：基础镜像、依赖安装、构建步骤、启动命令、`EXPOSE` 端口
2. **本地先跑通** —— `docker build` + `docker run`，确认服务真的能起来并响应请求（本地没跑通就别说能部署）
3. **推送镜像** —— 交给平台构建，或推到镜像仓库
4. **创建服务** —— 配端口、环境变量、启动参数（密钥走配置，不进代码）
5. **部署并验证** —— 拿到访问地址后**用真实请求打一次**，把响应贴给用户
6. **收尾** —— 设日志与扩缩容；说明资源用量与费用边界

## 三、真实资源清单（这是别人给不了的）

| 资源 | 用途 |
|---|---|
| PostgreSQL | 业务数据、事务、复杂查询 |
| 文档数据库 | 轻量结构化数据、快速起步 |
| 对象存储 | 文件、图片、备份 |
| 静态托管 | 前端、单页应用（交付一个网址） |
| 云函数 | 轻量 API、定时任务 |
| **云托管（容器）** | **任意语言的常驻服务** |
| 免费体验环境 | 零成本先把东西跑起来 |

## 四、交付标准（铁律）

1. **交付一个能访问的地址** —— 不是"部署说明"，不是"上线方案"，是一个真的打得开的 URL
2. **用真实请求验证** —— curl 或浏览器打开，把响应贴出来；没跑通就说没跑通
3. **密钥走平台配置** —— 环境变量 / 平台密钥管理，任何情况下不进代码与日志
4. **说清成本边界** —— 资源用量、是否在免费额度内、超出会怎样（不让用户被账单吓到）
5. **语言不设限但要能跑** —— 用户指定语言就按指定语言做；不熟的语言先查官方文档，不凭记忆编 API
6. **能说明为什么这么部署** —— 同一个服务为什么选容器而不是函数，给一句理由

## 五、常见坑

- **本地没跑通就上云**：容器起来了但服务没监听对端口 ⇒ 先本地 `docker run` 验证
- **端口写错**：容器内服务监听端口与平台配置的端口不一致 ⇒ 部署后表现为"打不开"
- **把长驻服务塞进函数**：WebSocket、后台线程、大内存任务不适合函数 ⇒ 用容器
- **环境变量没配**：代码里读到空值、连不上数据库 ⇒ 部署后第一件事看日志
- **忘记回收**：测试用的容器/函数忘了关，产生费用 ⇒ 交付时提醒用户
